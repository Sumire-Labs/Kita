# Architecture

## Modules

| Module | Responsibility |
| --- | --- |
| app | Bot本体。各機能、Discord・DB境界、設定・起動・終了 |
| common | Bot本体と音声プラグインで共用するプリセット識別・ファイル探索 |
| audio | Lavalink用プラグイン。WAVのデコード、FFT畳み込み、音声フィルター |

依存方向は`app → common`と`audio → common`です。`app`と`audio`は相互に依存しません。
`common`には両方から使用するものだけを置き、サードパーティーの実行時依存を持たせません。
Ticket・設定の契約はBot専用なので、`app`の各機能パッケージに置きます。

`app`内では`com.sumirelabs.kita`配下のパッケージで機能を分けます。

| Package | Responsibility |
| --- | --- |
| app | 設定ファイル、起動・終了、依存関係の組み立て |
| discord | JDA境界、コマンド受付、Components V2 UI、処理実行器 |
| storage | MariaDB、HikariCP、Flyway、リポジトリ実装 |
| basic | Ping、Avatar、FastFetch |
| settings | サーバー設定の契約と権限を検証する設定パネル |
| translation | 国旗と言語の対応、DeepL SDK、重複抑制 |
| previews | サービス別の取得と共通の表示 |
| tickets | チケット契約、受付、非公開チャンネル、担当者、履歴 |
| music | Lavalink接続、キュー、公開曲情報取得、プレイヤー |

新しい機能は`app`で`Command`やJDAリスナーを登録します。
外部データ取得・状態管理・表示を分離する方針は、パッケージ単位で維持します。

## Concurrency and persistence

外部通信とDB処理はGatewayイベントスレッドから分離し、最大64処理の仮想スレッド実行器を使用します。
混雑時はコマンドに再試行を案内し、自動処理はスキップします。
HikariCPのDB接続は最大12本。設定更新は行ロックとトランザクションで同時変更を保護します。
サーバー設定の全キーを文字列として保存するため、機能の追加時に設定用カラムを増やす必要はありません。

チケットにはサーバー・所有者ごとの有効チケット一意制約があります。
担当者登録とクローズ開始はDBの条件付き更新で競合を防ぎます。
5分以上中断している作成・クローズ処理は、Discord側のチャンネル状態を確認して回復します。
担当ロールはチケット作成時のIDを保存するため、設定変更が既存チケットの権限を変えることはありません。
作成先カテゴリの権限は引き継がず、必要なメンバー・担当ロール・Botの権限を明示します。

音楽キューはサーバーごとに分離し、各セッションの操作を直列化します。
キューは最大1000曲、戻る履歴は100曲。プレイヤーはサーバーごとに最後の1枚を15秒間隔で更新します。
音楽キュー・パネル位置は現在メモリ上にあり、再起動で失われます。

## HRIR

FFmpegでPCM・浮動小数点・WAVE_FORMAT_EXTENSIBLEをデコードし、出力レートへリサンプリングします。
対応チャンネル数は14・7・4・2。14チャンネルはHeSuViのFL-L、FL-R、FR-L、FR-Rを取り出します。
7チャンネルは前方の左右耳応答を左右対称に適用します。
2チャンネルは左右対称の応答として扱います。4チャンネルはLL、LR、RL、RRの順です。
ステレオの2入力・2出力に、512サンプル単位の分割FFT畳み込みを適用します。
FFTはJTransformsを使用。プリセットのFFT係数は最大16件をキャッシュします。
FFmpegでの再サンプリング後のインパルスの面積を、入力・出力レート比で補正します。
入力音源から7.1音源を生成するアップミックスは行いません。
プリセットと同じフォルダの`info.csv`から表示名と説明を読み込み、サブフォルダでは親のCSVも参照します。
HeSuViの`識別名;説明`形式を使用し、CSVにないファイルはファイル名を表示します。
選択IDは相対ファイル名から生成するため、表示名や説明を変更してもIDは変わりません。
セレクターの説明は100文字まで、選択中の詳細はプレイヤー内に最大1000文字まで表示します。
Lavalink 4.2.2のSpringがJava 25のクラス形式を読み取れないため、`audio`と共有型の`common`は
JDK 25でJava 21互換のバイトコードを生成します。Bot本体と実行環境はJava 25です。

## Build policy

VersioningがGit履歴とタグからバージョンを計算し、TokenEnvoyがビルドリソースへ埋め込みます。
DockerビルドにもGit履歴を含めます。CIはフル履歴を取得します。
依存関係のバージョンと解決結果を固定しています。
`checkArchitecture`で、手書きソースの最大160行とEmbed API禁止を検証します。
生成されたWrapperスクリプト・lockfile・検証メタデータは行数制限の対象外です。
`releaseBundle`はテスト後にBotの配布ZIP・音声プラグインJAR・チェックサム・メタデータを生成します。
通常のActionsビルドでは成果物を保存し、タグビルドでは同じ成果物をGitHub Releaseへ添付します。
詳しいタグ規則とステージの扱いは[ビルドとリリース](releases.md)を参照してください。

## Scaling

最初はBot・MariaDB・Lavalinkを1台に配置し、Discord推奨シャード数を使用します。
1000サーバー以上では、サーバー数に加えて同時音楽再生数とHRIRの長さを測定してください。
特にHRIRのCPUコストは同時再生数に比例します。
複数Lavalinkノードの設定、キューの永続化、複数Botプロセスのシャード割当は次の拡張点です。
現時点では、自動シャーディングは1プロセス内で行います。
